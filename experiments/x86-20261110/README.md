# node5005 Zen 5 单source优化

本目录已移除原始测试日志、CMake 缓存及重复的单值残差文件；结构化验证
和性能结果保留。历史清单的恢复方法见[归档说明](../README.md)。

目标：同一stout后24^3x64组态、同一原点单位source的完整12列，相对真残差<=1e-8。
复用层次，主指标完整Python求解API（布局转换和可靠检查包含；建层/IO/验证排除）。
现有稳定配置16MPI、每rank放置/建层16线程、求解12线程、batch2，保持不变。
直接SSH，没有调度独占保证；记录开始/结束对照，不称全局最优。

## 实机与官方依据

2026-11-10实际node5005：双路EPYC9755、256物理核、无SMT、8个NUMA，
sysfs每8个连续核共享L3，AVX512F/DQ/BW/VL等可用。节点初始负载约0.1。
AMD官方[架构白皮书](https://docs.amd.com/api/khub/documents/UIqhAbjRhgnzgzzdVU4pUw/content)
（2025-03，Zen5 CCD章节）说明每CCD至多8核共享32MB L3、每核1MB L2和完整512位数据通路。
[Zen5软件优化指南58455](https://docs.amd.com/v/u/en-US/58455_1.00)
（2024-08-15，rev1.00）为后续指令/布局设计参考，不把理论峰值当实测吞吐。

不直接改成32MPI×8线程：当前只按t切分，64时间片/块厚4只有16个聚合时间片，
32MPI不满足完整聚合块约束。新的空间MPI分解是另一项工程，未伪装成绑核参数。

## 第一轮假设和候选

问题：Clover每个输出行重新加载6个复输入，6行具有相同输入；现有16站点SIMD可复用。
模式1：一个手征加载6个复输入到12个ZMM，依次计算六行，减少重复源加载。
模式2：每次同时计算两行，复用每个输入并保持两条独立复累加链，降低活跃寄存器数。
系数仍按原packed布局，列累加次序和FP32运算表达式不变；掩码/非整16尾部保留。
这是寄存器内复用，不是跨source并行。两种模式均为noinline独立体，默认0保留旧路径。
风险：函数调用、代码膨胀、寄存器spill或矩阵系数流量占主导，可能抵消源加载节省。
开启需新进程，`LQCD_X86_CLOVER_REGISTERS=1/2`；不是动态求解配置。

## 第二轮：按自旋投影的符号结构计算

第一轮输入复用mode1中位6.175秒，相对旧6.190秒仅0.25%，不据此晋升。
mode2两行流水初步中位6.112秒，须待独立验证和结束对照；没有把初步值当最终胜出。
汇编确认mode1的12个输入向量驻留ZMM，不是寄存器spill导致收益小。
源加载仅是Clover部分流量，系数读取和其余Wilson hopping仍占主要工作。

下一假设：profile的主要热点Wilson hopping投影以一般复乘计算系数；DR自旋基中
非零gamma系数仅±1/±i，因此采用有符号加减和实虚部交换，省去零/单位乘法。
`LQCD_X86_SIGNED_PROJECTORS=1`启动时开启；模板实例保留默认通用路径，
系数不属于四种单位值时回退原表达式。重构与投影分别保留原先加法括号。
没有改变规范场矩阵乘法、半自旋重构关系、精度、预条件、迭代和残差门限。
潜在代价：分支、指令尺寸和寄存器调度可能抵消节省，必须看全12列。

`build_projector.sh`独立source-projector/build-projector，0/1分别通过同类11项CTest后，
`sequence_projector.py`运行proj0/proj1及旧库结束对照，Clover mode固定0以隔离机制。
每个进程自己建层；时钟、原点单位源、完整12列和标量/参考精度门限与第一轮相同。
所有任务沿同一worker顺序执行，不与普通求解重叠运行编译、验证或另一个性能实验。

## 第三轮：跨列站点片段复用

符号投影完整12列中位6.170秒，关闭6.206秒，旧稳定结束对照尚须核对。
算术指令减少未出现大收益，因此基于同一Wilson热点检验系数流量/调用开销。
原批处理每个块先完整计算第一列再计算第二列，单块864站点的links+diag约972KiB，
加源、输出和邻居数据超过1MiB L2，跨列再次读取可能已经驱逐系数。
候选按(块,站点片段,源列)访问，仍用原packed AVX512计算和相同halo。
16站点的links+diag是18KiB；64站点是72KiB。前者试图利用48KiB L1，后者
以较少内核调用、较大L2复用为对照。未更改存储布局，没有新增每次求解的packing。
`LQCD_X86_RHS_SITE_TILE=16/64`启动开启；默认0保留原循环。
这不是多source分组。所有操作仍在同一个source的12列内进行。
非packed、非AVX512、索引过大和单列入口保留原路径。
部分时间面/奇偶边界仍传原begin/end掩码；较小片段增加调用和尾部重复读取，可能退化。

`build_tile.sh`独立source-tile/build-tile，三种模式分别跑同类11项CTest。
`sequence_tile.py`等待第二轮全部闭合，运行tile0/tile16/tile64及旧库结束对照；
本轮Clover模式0、signed projector0，只检验循环次序。每组完整12列及独立标量验算。

16站点中位6.268秒，64站点6.179秒，关闭6.243秒。较细分块更慢，较粗分块虽
减少退化，却没有明显超过旧稳定版。支持“局部缓存收益不足抵消调用/调度代价”的
归因，但未采硬件cache miss事件，不能声称精确量化了L1/L2命中率或DRAM流量。
不晋升站点分块或符号投影版本。`confirm.py`等待第三轮闭合，再用第一轮精确
cc3804库测new2-confirm2和旧结束控制，避免把后续新增代码布局混进两行模式确认。
